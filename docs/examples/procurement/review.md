# 设备采购与审批 PRD 评审：核心规则未定，暂不具备排期条件

> 三份材料已能支撑场景、角色分工与主流程骨架，四模块边界与基础校验（人民币两位小数、数量>0、单价≥0、收货≤待收、一申请一订单）基本可直接落设计。但四项核心规则冲突或缺失：审批阈值 5,000 与 10,000 两套口径（且边界含义与比较基数未定）、财务复核环节在模块与状态机中不存在、主管自审替代规则空白、驳回后原单重提与新建单未定。叠加申请/订单/收货状态枚举不完整、并发只写目标无机制、关键字段（单号、供应商、行小计、取整规则）缺失，当前无法冻结状态机、字段矩阵与接口契约，也无法给出可信排期。建议先由业务方对 4 项规则拍板并形成书面结论，再进入详细设计与工时评估；在此之前可用静态原型验证交互，但不得把任一未定口径写死为事实。

## 一、 阻断性问题 (Blocking Issues)

### 1. 审批金额阈值存在 5,000 与 10,000 两套口径，8,600 演示单正好落在分歧区，审批路由不可编码

- **问题描述**：材料依据：01「金额不超过 5,000 元的申请，我同意就能买；超过 5,000 元还要财务复核。」02「采购总额小于 10,000 元，部门主管批准即可；达到 10,000 元才需要财务复核。」02 开头亦自述「本文件故意保留与访谈纪要之间的冲突」。影响：两套口径不仅数值不同，边界包含性也不同（≤5,000 免复核 vs <10,000 免复核），4,500 元演示单在两口径下同走主管审批，无法暴露差异；8,600 元的「设计工作站」在 01 下需财务复核、在 02 下仅主管审批，演示脚本、审批待办数据、状态机分支与边界用例全部无法定稿。比较基数也未定：按申请总额还是按明细合计、是否含税、比较前是否先四舍五入到分、阈值是硬编码还是可配置。需人工决定：采用哪一个阈值；边界是「不超过」还是「小于」；是否配置化及由谁维护；比较基数与取整时点。
- **采纳决策**：`EDITED`（说明: 合成业务方已在04人工确认单D01–D08决定；已写入当前PRD并保存，原评审不改。）

### 2. 财务复核在四个模块和状态枚举中没有落点，复核员角色无入口、无数据范围

- **问题描述**：材料依据：01 一期只覆盖「采购申请、审批待办、采购订单、收货登记」四模块；01「财务复核角色的归属和自审替代人还没有确定」；02 状态仅列「草稿、待审批、已批准、已驳回」；03 预置用户含「财务复核员「方宁」」。影响：无法判断财务复核是「审批待办」内的第二级节点还是独立入口，状态机缺「待财务复核/复核中」状态，审批记录缺对应动作类型；方宁能看到哪些部门、哪些金额的单据，待办如何排序，复核驳回后单据落到哪个状态（已驳回还是退回主管）均无定义。结果是高额单提交后在系统中没有合法停留点，主流程断链，审批待办列表查询条件也无法实现。需人工决定：财务复核是否纳入一期；若纳入，作为审批待办二级节点（主管通过后自动流转）；复核驳回的终态、可否修改重提、是否保留主管已通过记录。
- **采纳决策**：`EDITED`（说明: 合成业务方已在04人工确认单D01–D08决定；已写入当前PRD并保存，原评审不改。）

### 3. 主管自审被禁止但无替代人或兜底路径，主管本人提交申请时流程无合法审批人

- **问题描述**：材料依据：01「部门主管只能审核本部门申请，不能审核自己的申请」；02「主管不能审批自己的申请；但替代审批人如何选取没有约定」；01「财务复核角色的归属和自审替代人还没有确定」。影响：设计部主管周禾一旦提交申请，其单据既不能被自己审、也没有规则指定上级、代理人或管理员代审，提交入口是否直接阻断、阻断提示怎么写、审批待办按什么条件召回都无从实现；该场景必然出现在权限用例中。同类问题未覆盖财务复核（方宁既是复核员又提交申请时）、采购员是否可为自己的申请建单。需人工决定：替代审批人选取规则（固定上级/指定代理人/管理员兜底）；是否在提交时前置阻断并给出提示；替代审批是否单独留痕；自审限制是否扩展到财务复核与采购建单。
- **采纳决策**：`EDITED`（说明: 合成业务方已在04人工确认单D01–D08决定；已写入当前PRD并保存，原评审不改。）

### 4. 驳回后「原单修改重提」与「新建一单」未定，直接决定单号、版本、唯一订单约束与审计模型

- **问题描述**：材料依据：01「申请人希望能修改后重新提交，但没有讨论是否沿用单号」；02「有人建议驳回后新建一张单，有人希望原单修改后再次提交，处理方式待定」；02「一个申请只生成一个采购订单；再次点击不得生成第二张订单」。影响：若原单重提，需要版本号/审批轮次、单号不变、历史驳回理由与上一轮审批记录只读保留、重新进入待审批并重新生成待办；若新建单，需要记录与原单的关联、旧单保持已驳回终态且不可再操作，并明确「一申请一订单」的唯一约束作用在哪个维度。两种方案的表结构、单号生成时机、审计查询与测试用例完全不同。另有一处未定义：待审批状态下申请人能否修改标题/用途或撤回提交，材料只写「提交后不能直接编辑正在审批的明细」。需人工决定：采用哪种重提方式；若原单重提，轮次如何计数、是否重新走完整审批链；若新建单，是否允许从被驳回单复制；待审批是否允许撤回及撤回后状态。
- **采纳决策**：`EDITED`（说明: 合成业务方已在04人工确认单D01–D08决定；已写入当前PRD并保存，原评审不改。）

### 5. 申请、订单、收货三套状态枚举不完整且互相矛盾，缺申请侧收货汇总状态

- **问题描述**：材料依据：02 申请状态仅「草稿、待审批、已批准、已驳回」；02「未下单订单不能收货」与「未收、部分收货、已完成三种状态应可区分」并存；01「管理层希望能从申请一路查到审批、订单与累计收货，不做资产折旧或财务付款」。影响：订单到底有几种状态、「未下单」是订单状态还是「尚无订单」、已批准但尚未建单如何表达，三者不能同时成立；申请侧无「已下单/部分收货/已完成」汇总，管理层从申请追溯收货的诉求缺字段承载；「订单完成」判定（全部明细行累计收货数量=订购数量）未写成规则，部分收货与完成的边界只能靠实现者猜。状态字段是数据库、列表筛选、详情徽标和迁移校验的共同基础，不定则四模块列表与详情均不可开发，也无法编写全覆盖状态用例。需人工决定：统一状态字典（建议申请 5–6 值、订单 5 值含待下单/待收货/部分收货/已完成，是否含已取消）；一期是否支持取消订单；申请详情是否展示收货汇总及汇总口径（按数量还是按金额）。
- **采纳决策**：`EDITED`（说明: 合成业务方已在04人工确认单D01–D08决定；已写入当前PRD并保存，原评审不改。）

### 6. 并发与幂等只有目标没有机制，演示层「刷新后状态」与内存数据自相矛盾

- **问题描述**：材料依据：01「多人同时点审批时不能出现一张单既批准又驳回」；02「一个申请只生成一个采购订单；再次点击不得生成第二张订单」；02 验收要求检查「重复审批、重复建单、超额收货，以及刷新后的状态表现」；03「静态演示原型……使用内存中的虚构数据」。影响：需明确乐观锁版本号或条件更新（update ... where status='待审批'）、审批动作幂等键、订单 application_id 唯一约束、收货时行级锁与「本次数量≤待收数量」的事务内校验，以及冲突时返回 409 与前端刷新提示；否则接口契约与并发用例无法编写。同时内存数据刷新即重置，「刷新后的状态表现」在原型中无法成立，验收口径需写明是「刷新后回到种子数据」还是允许 localStorage 持久化。需人工决定：并发控制方案与冲突提示文案；重复点击是否复用同一幂等键；演示数据是否持久化或明确声明刷新重置。
- **采纳决策**：`EDITED`（说明: 合成业务方已在04人工确认单D01–D08决定；已写入当前PRD并保存，原评审不改。）

### 7. 权限只写了「谁能审」，缺数据范围、字段可见性与越权判定；管理员角色维护与四模块范围冲突

- **问题描述**：材料依据：01「申请人只看自己的申请」「主管只能审核本部门申请」「采购员只能对已批准申请建采购订单」「仓管只登记已下单订单」「系统管理员维护角色；本期演示预置人员，不做企业通讯录或组织系统集成」；02「采购员和仓管职责分离」；03 预置 7 个虚构用户含方宁。影响：缺少角色×单据×动作（读/建/改/状态迁移）的完整权限矩阵，尤其缺少财务复核员、系统管理员两行；「所属部门」是取自人员档案快照还是申请人可自由选择（旧表格里部门是自由填写的）未定，直接影响主管数据范围过滤；职责分离是否由系统强制（同一人不得同时具备采购员与仓管）未定；管理员「维护角色」在一期无对应模块与接口，若保留则范围膨胀，若移除需显式从范围中删除。越权提示与隐藏策略（前端隐藏还是服务端拒绝、返回 403 还是空列表）也未定义。需人工决定：管理员功能是否一期；部门字段来源；采购员跨部门可见范围；是否强制职责分离；越权统一返回口径。
- **采纳决策**：`EDITED`（说明: 合成业务方已在04人工确认单D01–D08决定；已写入当前PRD并保存，原评审不改。）

### 8. 关键字段与校验规则缺失，字段矩阵、表结构和金额边界用例无法定稿

- **问题描述**：材料依据：01 仅规定「申请至少有标题、所属部门、用途、期望到货日、物品明细。每行物品包含名称、规格、数量、单价。总额按行汇总……保留两位小数」；02 仅规定收货记录含「登记人、登记时间、本次数量」；03 列出旧表格字段（标题、申请人、部门、设备名、数量、预估单价、主管留言、采购备注），明确旧表「没有固定单号，没有结构化审批记录」。缺口包括：申请单号格式与生成时机（保存草稿即生成还是提交生成）、版本/轮次、提交时间、部门快照；物品行单位、行小计、数量是否必须为整数及上限、单价小数位与上限；总额取整规则（先四舍五入行小计再汇总还是汇总后取整，二者可能差 0.01）；标题/用途长度；期望到货日是否允许早于今天、与下单日/预计到货日的先后约束；驳回理由必填与长度；供应商字段（名称/联系人/税号/是否必填与唯一，一期是否做主数据）、订单号规则、下单人与下单时间、预计到货日是否可改；收货单号与备注、超额/零数量提示；审计字段（操作人/时间/动作/备注）的展示位置与保留期；搜索字段、默认排序、分页大小。影响：无这些定义就无法产出字段校验矩阵与表结构，4,999.99/5,000.00/5,000.01 这类金额边界用例没有预期结果，建单页与接口 requestBody 也无法冻结。需人工决定：供应商一期做自由文本还是主数据；数量是否限整数；金额与数量上限；总额取整口径。
- **采纳决策**：`EDITED`（说明: 合成业务方已在04人工确认单D01–D08决定；已写入当前PRD并保存，原评审不改。）

## 二、 优化建议 (Other Suggestions)

- 当前状态机没有「待审批→草稿」的路径，误提交无出路，只能依赖审批人驳回，既污染审批记录也影响待办统计。建议明确是否支持撤回、撤回是否留痕、撤回后能否继续编辑，并在权限矩阵中给出申请人操作位。若不支持，应在提交前加二次确认并写入不做清单。
- 01 只要求「页面需要搜索、状态筛选、分页、表单校验、详情和空状态」。建议明确各列表可搜索字段（单号/标题/申请人/供应商）、筛选项枚举、默认排序（建议提交时间或创建时间倒序）、每页条数、空状态与无结果文案。这些直接决定前端参数与测试断言，成本低但缺失时验收容易扯皮。
- 建议在阈值拍板后固定覆盖 4,499.99 / 4,500.00 / 4,999.99 / 5,000.00 / 5,000.01 / 8,600.00 / 9,999.99 / 10,000.00 / 10,000.01，并同时验证「刚好等于边界」与「多一分」两种情况，避免实现时把「不超过」写成「小于」。
- 03 说明旧表没有固定单号、结构化审批记录与分批收货记录，而一期是替换聊天+表格。建议明确「不迁移、只做新单据」或「导入为只读历史申请（无审批链）」。这会影响是否需要导入脚本、历史查询入口与初版数据量，属于排期前的范围确认项。
- 材料只覆盖正常下单与收货，未定义供应商无法供货、预计到货日延期、订单取消等情形。建议一期至少给出「不支持变更/取消」的显式说明与对应提示，或定义预计到货日可修改且不影响状态。否则上线后必然以缺陷形式回流。
- 01 已明确不做支付、邮件、短信、供应商接口、正式权限集成、资产折旧与财务付款；02 明确不做退货、收货撤销、超额收货。建议集中成章节并给出用户触发这些操作时的提示文案，减少验收阶段的范围争议。
- 02 要求「任何状态变化应显示操作人、时间、动作和备注」，但未说谁可见、是否可导出、保留多久、是否允许修改。建议一期定为只读时间线，申请人可见自己单据的审批与收货记录，主管/采购/仓管按数据范围可见，并明确不可编辑。
- 02 的验收关注点写得可执行（新建→校验→提交→主管审→建单下单→两次收货→完成记录），但没有 AC 编号与预期结果。建议编号后逐条给出通过条件，测试用例可直接引用，也便于回归时判断哪些条目受阈值决策影响需要重跑。
