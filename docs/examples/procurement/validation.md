### 保留的原型缺陷

原始 HTML 不做静默修复，下载包和录屏使用同一生成结果。以下是公开限制，不是已完成特性：

- “新建申请”对所有角色可见，采购员、仓管能从普通界面新建并提交，违反当前稿权限要求。正式实现必须修正，不能用此原型验收角色安全。
- 主管/财务的草稿编辑与提交入口不完整。代审缺专门标记和完整留痕，未覆盖主管本人申请场景。
- 驳回单先保存为草稿再提交会复用审批轮次；普通保存/提交版本也会增加，版本与轮次存在脱钩。
- 缺搜索、筛选、分页和显式排序；日期基准固定为案例日期，未来重放不等于按当天校验。
- 完整操作时间线及申请详情累计收货量尚未实现；一笔 8,600 元已批准种子缺财务历史。

因此，这是**经过部分交互验证的真实模型原型及工程交付草案**，不是完成全部业务验收的采购产品。测试包中的用例是待执行设计，不能把生成用例数量当成测试通过数量。技术方案里的表/API 是待开发设计，估算也不是实际消耗或承诺工期。

### 技术方案仍须人工校核

独立审查还发现以下技术草案问题，原文保持不变供核对：

- 模型选择 Boot 3.3.x、Vue 3.4、Vite 5，不是工作台仓库冻结的实际运行版本；不能将技术草案当作当前项目版本说明。
- 财务查询扩展到历史申请，超出人工基线确认的数据范围。
- 收货示例先过滤数量大于0的行再校验负数，混合负数与合法行时可能漏拒绝负数；正式实现应整笔拒绝非法输入。
- “同一行第二次并发收货必然失败”的说明过强。仅凭不超过订购量的条件，余量足够时两个事务都可能合法成功；需按业务语义明确竞争验收。

这也是保留来源、独立当前稿与人工评审环节的原因。下载得到的是可讨论、可追溯的草案集合，不是已消除所有设计缺陷的交付承诺。
