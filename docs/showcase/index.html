Step 01

原始输入材料与规则源头

真实业务中，需求往往由多位业务方在不同时间口头提供或表格补充，不可避免存在规则漏洞与矛盾

⚠️ 核心冲突聚焦：两份材料中的审批金额阈值完全不一致

📄 01-客户访谈纪要.md（业务主管口头诉求）

📄 02-业务规则补充.md（运营负责人补充表格）

# 设备采购与审批：客户访谈纪要 > 完全虚构的公开演示材料。组织、人物、单据与金额均为合成数据，不对应任何客户。 ## 场景与目标 虚构组织「青岚工坊」有三个部门：设计部、研发部、运营部。办公设备采购目前依赖聊天和表格：申请人发需求，主管回复同意，采购员自行下单，仓管再核对到货。月底常常不知道某笔采购是否已经审批、是否收齐。 一期做一个桌面端设备采购工作台，覆盖四个模块：采购申请、审批待办、采购订单、收货登记。 ## 角色与流程 - 申请人只看自己的申请，可保存草稿、编辑草稿、提交，查看驳回理由。 - 部门主管只能审核本部门申请，不能审核自己的申请。 - 采购员只能对已批准申请建采购订单，并录入供应商、预计到货日和明细。 - 仓管只登记已下单订单的实际收货数量，可分多次收货，全部收齐后订单完成。 主管在会上说：“金额不超过 5,000 元的申请，我同意就能买；超过 5,000 元还要财务复核。”财务复核角色的归属和自审替代人还没有确定。 ## 用于演示的设备 - 显示器：2 台，单价 1,800.00 元。 - 扩展坞：2 个，单价 450.00 元。 - 合计：4,500.00 元。 - 第二笔申请：设计工作站 1 台，单价 8,600.00 元，用于观察高额审批规则。
Step 02

评审发现：为什么 8,600 元申请暴露了规则撕裂？

Hermes Agent 评审模式执行深度交叉比对，在编码前阻断了导致系统故障的 8 项关键缺陷

🧪 规则冲突模拟器：点击不同金额查看审批路径分歧

4,500 元的申请在两套规则下表现一致，但 8,600 元的申请正好落在分歧区间：

按《01-客户访谈纪要》（5,000 元线）：
超过 5,000 元 → 必须财务二级复核
按《02-业务规则补充》（10,000 元线）：
小于 10,000 元 → 主管终审即可（无需财务复核）
⚠️ 规则冲突爆发！8,600 元的设计工作站申请落入分歧区间。若按访谈纪要需要财务复核，按补充规则主管批准即可买。若直接交给研发开发，系统将出现重大越权漏洞或流程卡死！

Hermes Agent 评审识别出的 8 项阻断性问题（节选）：

阻断 1. 审批金额阈值 5,000 与 10,000 两套口径冲突

8,600 元演示单正好落在分歧区。数值不同且边界包含性不同（≤5,000 免复核 vs <10,000 免复核），审批状态机分支与用例无法定稿。

阻断 2. 财务复核在四个模块中没有落点

状态机中缺少“待财务复核”，复核员方宁无专用入口、无数据范围过滤，高额单据提交后将成为死单。

阻断 3. 主管自审被禁止但无替代人或兜底路径

设计部主管周禾一旦提交申请，其单据既不能被自己审、也没有规则指定代理人，流程无合法审批人。

阻断 4. 驳回后「原单重提」与「新建单」未定

决定单号生成时机、版本计数、历史审批留痕与“一申请一订单”唯一约束作用的表结构与测试用例。

阻断 5. 申请、订单、收货三套状态枚举不一致

未定义“订单完成”的判定准则（全部行累计收货数=订购数），申请详情缺少关联的收货汇总字段承载。

阻断 6. 并发与幂等只有口头目标没有机制

多人同时点击审批防并发批准/驳回、防重复建单、收货超收拦截缺少乐观锁或事务条件校验契约。

Step 03

人工决策与当前稿独立管理

AI 决定分析与草案，人类决定业务规则：原始结果只读归档，人工修改保存为独立当前稿

D01：审批额度最终拍板

业务方确认采用 5,000.00 元边界：单据总额 ≤5,000.00 元主管审批通过即批准；>5,000.00 元（包括 8,600.00 元）必须经财务二级复核。5,000.00 元无需财务，5,000.01 元需要。

D02：财务复核入口与状态

财务复核纳入「审批待办」模块，按角色展示。申请单状态统一为：草稿、待主管审批、待财务复核、已批准、已驳回。两级驳回均回到已驳回。

D03：自审与代理授权

设计部主管周禾的申请由研发部主管许原代审；研发部主管许原的申请由设计部主管周禾代审；代审行为记入审计时间线，杜绝无审批人死单。

D04：驳回后原单修改重提

驳回后申请人修改原单重新提交，单号保持不变，版本与审批轮次递增（Version+1）；上一轮审批记录只读留痕，新一轮走完整审批链。

💡 为什么工作台必须坚持“原始结果不可变，人工修订独立保存”？
传统工具常将 AI 生成物直接覆盖或由用户在线涂改，导致后续生成步骤出现严重的“上下文漂移”与幻觉。Hermes PRD 工作台将 Agent 原始输出只读固化为版本快照，人类产品经理的校对、决策单独存为当前稿（Current Draft）。下游的原型、测试用例、技术方案生成只读取人类校对后的当前稿，确保交付工程具备绝对确定性。
