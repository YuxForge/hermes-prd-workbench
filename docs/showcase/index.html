Step 01

原始输入材料与规则源头

真实业务中，需求往往由多位业务方在不同时间口头提供或表格补充，不可避免存在规则漏洞与矛盾

⚠️ 核心冲突聚焦：两份材料中的审批金额阈值完全不一致

📄 01-客户访谈纪要.md（业务主管口头诉求）

📄 02-业务规则补充.md（运营负责人补充表格）
“采购总额小于 10,000 元，部门主管批准即可；达到 10,000 元才需要财务复核。”
# 设备采购与审批：客户访谈纪要 > 完全虚构的公开演示材料。组织、人物、单据与金额均为合成数据，不对应任何客户。 ## 场景与目标 虚构组织「青岚工坊」有三个部门：设计部、研发部、运营部。办公设备采购目前依赖聊天和表格：申请人发需求，主管回复同意，采购员自行下单，仓管再核对到货。月底常常不知道某笔采购是否已经审批、是否收齐。 一期做一个桌面端设备采购工作台，覆盖四个模块：采购申请、审批待办、采购订单、收货登记。 ## 角色与流程 - 申请人只看自己的申请，可保存草稿、编辑草稿、提交，查看驳回理由。 - 部门主管只能审核本部门申请，不能审核自己的申请。 - 采购员只能对已批准申请建采购订单，并录入供应商、预计到货日和明细。 - 仓管只登记已下单订单的实际收货数量，可分多次收货，全部收齐后订单完成。 主管在会上说：“金额不超过 5,000 元的申请，我同意就能买；超过 5,000 元还要财务复核。”财务复核角色的归属和自审替代人还没有确定。 ## 用于演示的设备 - 显示器：2 台，单价 1,800.00 元。 - 扩展坞：2 个，单价 450.00 元。 - 合计：4,500.00 元。 - 第二笔申请：设计工作站 1 台，单价 8,600.00 元，用于观察高额审批规则。
Step 02

评审发现：为什么 8,600 元申请暴露了规则撕裂？

Hermes Agent 评审模式执行深度交叉比对，在编码前阻断了导致系统故障的 8 项关键缺陷

🧪 规则冲突模拟器：点击不同金额查看审批路径分歧

4,500 元的申请在两套规则下表现一致，但 8,600 元的申请正好落在分歧区间：

按《01-客户访谈纪要》（5,000 元线）：
超过 5,000 元 → 必须财务二级复核
按《02-业务规则补充》（10,000 元线）：
小于 10,000 元 → 主管终审即可（无需财务复核）
⚠️ 规则冲突爆发！8,600 元的设计工作站申请落入分歧区间。若按访谈纪要需要财务复核，按补充规则主管批准即可买。若直接交给研发开发，系统将出现重大越权漏洞或流程卡死！

Hermes Agent 评审识别出的 8 项阻断性问题（节选）：

阻断 1. 审批金额阈值 5,000 与 10,000 两套口径冲突

8,600 元演示单正好落在分歧区。数值不同且边界包含性不同（≤5,000 免复核 vs <10,000 免复核），审批状态机分支与用例无法定稿。

阻断 2. 财务复核在四个模块中没有落点

状态机中缺少“待财务复核”，复核员方宁无专用入口、无数据范围过滤，高额单据提交后将成为死单。

阻断 3. 主管自审被禁止但无替代人或兜底路径

设计部主管周禾一旦提交申请，其单据既不能被自己审、也没有规则指定代理人，流程无合法审批人。

阻断 4. 驳回后「原单重提」与「新建单」未定

决定单号生成时机、版本计数、历史审批留痕与“一申请一订单”唯一约束作用的表结构与测试用例。

阻断 5. 申请、订单、收货三套状态枚举不一致

未定义“订单完成”的判定准则（全部行累计收货数=订购数），申请详情缺少关联的收货汇总字段承载。

阻断 6. 并发与幂等只有口头目标没有机制

多人同时点击审批防并发批准/驳回、防重复建单、收货超收拦截缺少乐观锁或事务条件校验契约。

Step 03

人工决策与当前稿独立管理

AI 决定分析与草案，人类决定业务规则：原始结果只读归档，人工修改保存为独立当前稿

D01：审批额度最终拍板

业务方确认采用 5,000.00 元边界：单据总额 ≤5,000.00 元主管审批通过即批准；>5,000.00 元（包括 8,600.00 元）必须经财务二级复核。5,000.00 元无需财务，5,000.01 元需要。

D02：财务复核入口与状态

财务复核纳入「审批待办」模块，按角色展示。申请单状态统一为：草稿、待主管审批、待财务复核、已批准、已驳回。两级驳回均回到已驳回。

D03：自审与代理授权

设计部主管周禾的申请由研发部主管许原代审；研发部主管许原的申请由设计部主管周禾代审；代审行为记入审计时间线，杜绝无审批人死单。

D04：驳回后原单修改重提

驳回后申请人修改原单重新提交，单号保持不变，版本与审批轮次递增（Version+1）；上一轮审批记录只读留痕，新一轮走完整审批链。

💡 为什么工作台必须坚持“原始结果不可变，人工修订独立保存”？
传统工具常将 AI 生成物直接覆盖或由用户在线涂改，导致后续生成步骤出现严重的“上下文漂移”与幻觉。Hermes PRD 工作台将 Agent 原始输出只读固化为版本快照，人类产品经理的校对、决策单独存为当前稿（Current Draft）。下游的原型、测试用例、技术方案生成只读取人类校对后的当前稿，确保交付工程具备绝对确定性。

旗舰案例 · 设备采购与审批系统 PRD 规格明细

以人工校对后的生产基线（Current Baseline）呈现，与原始 Agent 输出保持只读隔离

可直接指导研发开工

📦 模块一：采购申请 (purchase-request)

  • 单号生成机制：保存草稿时由系统生成全局唯一申请单号（前缀 SQ + 年月日 + 6位递增流水，如 SQ20261019000001），初始化版本 version=1、轮次 round_no=1。
  • 草稿暂存与全量校验：保存草稿允许缺失标题或用途暂存，明细单价/数量合法即可算出行金额；点击“提交审批”才执行全量必填校验（标题 1–100 字、用途 1–500 字、期望到货日不早于当天、至少一行明细）。
  • 驳回重提机制 (D04)：单据被驳回后申请人可在原单修改重新提交；单号保持不变，版本与审批轮次各自增 1 (version+1, round_no+1)；上一轮审批记录与驳回理由只读归档，新一轮重走完整审批链。
  • 不可编辑与防越权：提交审批后或已批准单据整单永久只读，申请人侧所有编辑与撤回入口消失，服务端返回 403 严格防越权。

⚖️ 模块二：审批待办 (approval-todo)

  • 金额路由拍板 (D01)：申请明细按行金额（数量×单价）汇总结算；总额 ≤ 5,000.00 元 主管通过即批准 (APPROVED)；总额 > 5,000.00 元（含 5,000.01 与 8,600.00 元）主管通过后推进至待财务复核 (PENDING_FINANCE)，财务通过后才进入已批准。
  • 角色待办隔离：主管仅看本部门待主管审批单据；财务复核员可跨部门看待财务复核单据。
  • 自审拦截与代审授权 (D03)：主管与财务本人提交申请严禁自审；设计部主管周禾与研发部主管许原互为对方本人申请代审，代审操作明确记录代审人与时间线，杜绝死单。
  • 驳回规则：驳回必须填写 1–200 字理由，缺失理由无法驳回；驳回后单据流转至已驳回终态 (REJECTED)。

🛒 模块三：采购订单 (purchase-order)

  • 建单权限与前提：仅已批准 (APPROVED) 申请允许采购员创建采购订单；草稿、审批中、已驳回单据均无建单入口。
  • 一申请一订单约束 (D05)：数据库建立 application_id 唯一约束，一个申请单最多生成一个订单；重复点击建单自动拦截并跳转已有订单详情。
  • 批准版本快照锁定：订单明细从批准版本申请快照继承，单价、数量、品名永久锁定，采购员不可篡改。
  • 下单推进：采购员填写供应商（必填自由文本 1–100 字）与预计到货日（不早于下单日）后确认下单，状态推进至待收货 (PENDING_RECEIVE)。

📥 模块四：收货登记 (receiving)

  • 角色专有与职责分离：仅仓管角色可在待收货/部分收货状态登记到货；采购员无收货入口。
  • 按行实收与超收拦截 (D05/D06)：按明细行录入本次实收数量；校验本次实收数 ≤ 待收量；严厉拦截超额收货、负数或小数。
  • 分批到货与只读记录：允许多次分批到货；每次生成只读收货单记录（包含记录号、登记人、时间、各行实收数量）；累计已收量原子累加。
  • 订单完成判定：全部明细行累计已收数量等于订购数量时，订单推进至“已完成”，关闭后续收货入口。

PR-002 EXCEPTION 采购申请 · 提交校验
优先级: P0
提交审批执行全量必填校验并进入待主管审批

PR-003 BOUNDARY 采购申请 · 字段边界
优先级: P0
日期、数量、单价格式非法不保存，合法边界值可保存

前置条件: 正式系统环境；订单 DD-0006 待收货：显示器 订购2 累计0 待收2。
操作步骤: (1) 两个会话同时打开收货登记，均填显示器本次 2。 (2) 会话A提交成功后，会话B立即提交。 (3) 核对会话B响应、订单累计与收货记录条数。 (4) 再测两会话分别提交 1 的场景。
预期结果: 正式系统在同一事务内校验剩余量，只有一方成功，另一方返回 409 并提示刷新；累计已收不超过2，记录不重复；两会话各填1时若均成功则累计为2并变已完成，若一方409则累计为1且状态部分收货，两种结果均不得超出订购量。
RC-006 PERMISSION 收货登记 · 权限与数据范围
优先级: P1
仓管不可建单下单，采购无收货动作，财务不可读订单与收货
前置条件: 存在待收货订单与已完成订单各一张；已登录各角色账号。
操作步骤: (1) 以白舟登录：核对无新建订单、下单入口，可登记收货。 (2) 以苏青登录：核对订单详情无收货入口，收货记录只读可见。 (3) 以方宁登录：核对订单列表与收货记录均不可见。 (4) 以林沐登录：核对仅见本人申请关联订单与收货进度的只读信息。
预期结果: 白舟无建单/下单动作；苏青无收货动作但可查看记录；方宁列表与详情均无订单及收货数据；林沐仅见本人关联进度且只读；正式系统需补测服务端 403，前端隐藏不算通过。

GET /api/v1/purchase-requests/{id}
申请详情聚合读：主表、行明细、全部审批轮次、只读时间线、订单与累计收货进度（财务角色整体省略订单段）
PUT /api/v1/purchase-requests/{id}

GET /api/v1/approvals/todo
审批待办分页列表；主管看本部门 PENDING_MANAGER（排除本人申请），财务看跨部门 PENDING_FINANCE（排除本人申请），同一模块按角色返回
POST /api/v1/approvals/{applicationId}/decision
审批决策（通过/驳回）；事务内校验归属性、自审、理由，条件更新状态并写审批记录；≤5000.00 元主管通过即批准，>5000.00 元进入财务复核
GET /api/v1/purchase-orders
订单分页列表；采购看全部，仓管只看待收货/部分收货，申请人/主管只看本人或本部门申请关联订单，财务 403
POST /api/v1/purchase-orders
在已批准申请上创建订单：校验状态与唯一性，复制批准版本行快照，状态 PENDING_ORDER，不修改申请状态
GET /api/v1/purchase-orders/{id}
订单详情：快照行（订购数/累计已收/待收）、只读时间线、收货历史与本次可收数量；收货表单数据由本接口提供
POST /api/v1/purchase-orders/{id}/place
下单：填供应商与预计到货日，校验后状态 PENDING_ORDER → PENDING_RECEIVE，写 ordered_at
POST /api/v1/purchase-orders/{id}/receipts
收货登记：按行提交本次到货量，空/0 行忽略，全 0 拦截，逐行条件累加防超收，同一事务写收货头/明细并推进订单状态
GET /api/v1/session/me
当前会话：返回用户、角色、部门与前端可用的能力开关（仅用于界面渲染，服务端仍独立鉴权）

1. 乐观锁状态与版本条件更新 (防审批并发冲突)

针对审批待办多人同时点击批准/驳回，正式业务系统采用基于 status 与 row_version 的条件更新，更新受影响行数不为 1 时立即回滚并返回 HTTP 409 Conflict：

UPDATE pr_application SET status = 'APPROVED', row_version = row_version + 1, updated_at = NOW() WHERE id = ? AND status = 'PENDING_MANAGER' AND row_version = ?;

2. 事务内原子累加防超收 SQL (核心收货安全)

针对分批收货与多次到货并发场景，在单事务内执行原子条件累加校验，确保无论如何并发，累计已收数量绝不可能超过订购数量：

-- 单条 SQL 在行锁内完成原子校验累加，返回更新行数为 0 则抛出超收异常整单回滚 UPDATE po_order_item SET received_quantity = received_quantity + ?, row_version = row_version + 1 WHERE id = ? AND (received_quantity + ?) <= order_quantity;

3. 一申请一订单唯一约束 (防重复下单)

在采购订单主表 po_order 上对 application_id 建立 UNIQUE 唯一索引 uk_application_id，从数据库物理层杜绝因网络重试或双击产生第二张订单。
